# CI/CD analysis: why `build-and-push (frontend)` takes ages

## The pipeline today

- **`deploy.yml`** (runs on every PR to `main`, and on every push to `main`):
  - `validate-frontend`: `npm ci` → lint → typecheck → test → `npm run build` → then a **Docker build of the FE image** (`push: false`) with **no cache** on every PR.
  - `build-and-push` (push to `main` only): matrix of `frontend` + `backend`, each `docker/build-push-action` with **`platforms: linux/arm64`** on an **x86 `ubuntu-latest` runner**, `cache-from/to: type=gha, **mode=min**`.
- **`frontend-new-ci.yml`**: separate workflow with path filters running the *identical* `npm ci → lint → typecheck → test → build` sequence.

## Root causes of the slow step (in order of impact)

**1. The whole JS toolchain runs under QEMU emulation.**
Your production server is ARM64 (per `docs/deployment.md`/ADR-002: "builds ARM64 images"), so the workflow builds `linux/arm64` on x86 GitHub runners. BuildKit runs every `RUN` step emulated via binfmt/QEMU — that's `npm ci` in `node:20-alpine` **and** `npm run build` (tsc + vite + Tailwind v4). QEMU is typically 2–5× slower than native, and npm is IO/CPU-bound: this single fact is worth **15–25 min** of the step. The `VITE_API_BASE_URL`/`BUILD_SHA` build args and the `printf version.json` step are trivial; the emulated `npm ci` + `vite build` are the cost.

**2. `cache-to: type=gha, mode=min` defeats the Docker layer cache.**
`mode=min` exports **only the final layer** to the Actions cache. So the `npm ci` layer is never persisted — a full `npm ci` re-runs on **every build**, even when `package-lock.json` didn't change at all. (With `mode=max`, an unchanged lockfile would skip it; but that still leaves QEMU for any dependency change, and GHA caches expire after 7 days by default.)

**3. The FE image contains a toolchain it doesn't need.**
The final image is `nginx:1.27-alpine` + static `dist/` + one config file. `dist/` is architecture-independent, yet the current `Dockerfile` compiles the entire app inside the emulated ARM64 container. **There is zero technical reason to run npm/Vite in Docker at all** for this app.

**4. Duplicated work on PRs (slows PR feedback, same root issue).**
A frontend PR runs the full `npm ci + lint + typecheck + test + build` **twice** — once in `deploy.yml` (`validate-frontend`, which has *no path filter*, so it also runs for backend-only PRs) and once in `frontend-new-ci.yml`. On top of that, `validate-frontend` does a cacheless QEMU Docker build on **every** PR.

## Recommended fix (biggest bang for buck, smallest change)

**Move the JS build out of Docker; let Docker only assemble static files.**

1. New CI-only Dockerfile (no `RUN` steps at all):
   ```dockerfile
   FROM nginx:1.27-alpine
   COPY nginx.prod.conf /etc/nginx/conf.d/default.conf
   COPY dist/ /usr/share/nginx/html/
   EXPOSE 80
   # keep existing HEALTHCHECK
   ```
   Keep the current multi-stage `Dockerfile` untouched for local `docker compose` dev.
2. In `build-and-push` (frontend matrix entry): before the docker step, run `actions/setup-node` (with npm cache) + `npm ci` + `VITE_API_BASE_URL= npm run build` + `printf '{"revision":"<sha>"}' > dist/version.json` — all **native on x86**, which is fast (~1–3 min total with the npm cache). Then `docker build` with the RUN-free file for `linux/arm64`. With zero `RUN` steps, **no QEMU work happens at all** — it's just pulling the arm64 nginx base and copying static files, which takes seconds. The GHA cache then usefully skips the `dist` layer on backend-only pushes to `main` (identical `dist` content).
3. Do the same in `validate-frontend` (PR gate) — it now verifies the *exact* production assembly without QEMU cost.
4. Remove `frontend-new-ci.yml` — it's a strict duplicate of `validate-frontend` (same 5 steps, and `deploy.yml` runs on all PRs). One caveat to check: if your branch-protection rules require the status check named `Frontend New CI / quality`, update the required-checks list when deleting it.

**Expected result:** the `build-and-push (frontend)` step drops from ~15–25 min to roughly **3–5 min** (native npm/build + GHCR push dominate), and PR validation loses ~10–15 min of QEMU Docker work plus one fully duplicated job.

## Smaller/optional improvements

- **Don't rebuild the FE on backend-only pushes:** the `build-and-push` matrix has no path filter, so every `main` push rebuilds and re-pushes both images. With fix #1 this is cheap, but you could gate it if you want the `latest`/branch tags to move less. (Careful: don't `needs`-gate `deploy` on a skippable validation job — skipped needs propagate and would block deployments.)
- **Backend has the same QEMU problem** (`uv sync` in-image for arm64), just less dramatic. A cheap win there: switch its `cache-to` to `mode=max` so the `uv sync` layer is exported and hits when `uv.lock` is unchanged. I'd treat this as a follow-up, separate from the FE work.
- **`npm ci` in CI** installs `playwright` (devDep) though tests run under jsdom — you could trim it, but with the Actions npm cache this is a minor saving.
- **GitHub ARM runners** (`ubuntu-24.04-arm`, public preview) would also remove QEMU, but they're preview/availability-limited for private repos; the prebuilt-`dist` pattern is more robust and doesn't depend on runner availability, so I'd prefer it.
